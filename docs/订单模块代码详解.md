## 1. 模块概览

订单模块是整个系统的“交易核心”，负责把一次预订从“房客提交”到“完成/取消”的全过程记录下来，并维护库存与房间分配的一致性。它对外暴露两类接口：

- **房客端** `/api/orders`：创建订单、查我的订单、查详情、取消订单；
- **房东端** `/api/admin/orders`：分页查全部订单、查详情、确认、拒绝、办理入住、完成订单。

内部依赖三个兄弟模块：

| 依赖模块 | 用途 |
| --- | --- |
| `roomtype` | 校验房型是否存在、是否上架，补全房型名称 |
| `room` | 分配物理房间、统计整段日期空闲房间数 |
| `calendar` | 逐日校验库存、原子扣减 / 归还库存 |

订单模块本身不定义价格规则——价格完全来自 `room_calendar`，订单只在下单瞬间把总价快照到 `orders.total_amount`。

## 3. 数据表设计

订单模块对应 4 张表，全部在 `src/main/resources/db/schema.sql` 中定义。

### 3.1 `orders` 订单主表

一次预订一条记录。关键字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK AUTO_INCREMENT | 主键 |
| `order_no` | VARCHAR(32) UNIQUE | 订单号，业务唯一标识 |
| `user_id` | BIGINT | 下单房客 ID |
| `room_type_id` | BIGINT | 预订房型 ID |
| `check_in_date` | DATE | 入住日期（含当天） |
| `check_out_date` | DATE | 离店日期（不含当天） |
| `nights` | INT | 晚数 = check_out − check_in |
| `room_count` | INT | 预订间数 |
| `total_amount` | DECIMAL(10,2) | 订单总金额（元） |
| `status` | VARCHAR(20) | 状态，见 OrderStatus |
| `contact_name` / `contact_phone` | VARCHAR | 联系人 |
| `remark` / `cancel_reason` | VARCHAR | 备注 / 取消原因 |
| `created_at` / `updated_at` | DATETIME | 创建 / 更新时间（DB 默认值） |

关键索引：`(room_type_id, check_in_date, check_out_date)` 组合索引，服务于“查某房型某区间是否被占用”；`status` 单列索引，服务于后台按状态筛选。

### 3.2 `order_room` 订单 ↔ 物理房间

一单订多间就有多行。字段：`id`、`order_id`、`room_id`。
唯一约束 `(order_id, room_id)`，防止同一间房被重复分给同一单。

### 3.3 `order_stay` 订单逐晚占用

`[check_in, check_out)` 内每晚一行。字段：`id`、`order_id`、`stay_date`。
**存在的意义**：取消时不需要再从 `check_in/check_out` 反推日期，直接按这些行逐晚归还库存，保证归还的晚数与扣减的晚数精确一致。

### 3.4 `order_log` 状态流转日志

每次状态变更追加一条。字段：`id`、`order_id`、`from_status`、`to_status`、`operator_id`、`remark`、`created_at`。
创建订单时 `from_status` 为 `NULL`。用于订单详情页的“状态轨迹”展示。

> 注意：这 4 张表与 `room_calendar`、`room`、`users` 之间**没有数据库外键约束**，引用完整性由 Service 层校验。这是课程项目为了灵活建表和灌演示数据做的取舍。

## 4. 订单状态机 OrderStatus

文件：`order/enums/OrderStatus.java`

它不是枚举类，而是一个 `final` 工具类，用常量定义状态，用两张 `Map` 定义流转规则和文案：

```java
public static final String PENDING    = "PENDING";     // 待确认
public static final String CONFIRMED  = "CONFIRMED";   // 已确认
public static final String CHECKED_IN = "CHECKED_IN";  // 已入住
public static final String COMPLETED  = "COMPLETED";   // 已完成
public static final String CANCELLED  = "CANCELLED";   // 已取消
```

流转表（`TRANSITIONS`）：

| 当前状态 | 可流转到 |
| --- | --- |
| `PENDING` | `CONFIRMED`、`CANCELLED` |
| `CONFIRMED` | `CHECKED_IN`、`CANCELLED` |
| `CHECKED_IN` | `COMPLETED` |
| `COMPLETED` | （终态） |
| `CANCELLED` | （终态） |

两个静态方法：

- `canTransition(from, to)`：查 `TRANSITIONS`，判断是否允许流转；
- `text(status)`：查 `TEXTS` 返回中文文案，未知状态原样返回编码。

设计上用常量而不是 Java `enum`，是因为状态值要直接存进数据库 `VARCHAR` 列并在前后端之间透传，字符串常量更直观，前端也能直接用编码做判断。

## 5. 实体层 entity

四个实体都是纯 POJO，用 MyBatis-Plus 注解映射表名和主键，字段都有中文注释，方法都是标准 getter/setter。

### 5.1 `Order`

对应 `orders` 表。类注释点明三个关键约定：

1. 一次预订一条记录；
2. 入住区间是半开区间 `[checkInDate, checkOutDate)`；
3. 状态流转见 `OrderStatus`。

字段语义见 3.1。`@TableName("orders")` 映射表名，`@TableId(type = IdType.AUTO)` 声明自增主键。金额用 `BigDecimal` 避免浮点误差，日期用 `java.time.LocalDate` / `LocalDateTime`。

### 5.2 `OrderRoom`

只有 `id`、`orderId`、`roomId` 三个字段，是订单与物理房间的多对多关联表。

### 5.3 `OrderStay`

只有 `id`、`orderId`、`stayDate`。类注释强调“取消时按这些日期逐晚归还库存”，这是它存在的核心理由。

### 5.4 `OrderLog`

`fromStatus`、`toStatus`、`operatorId`、`remark`。`fromStatus` 允许为 `null`（创建订单那条日志）。

## 6. 数据传输层 dto

### 6.1 `CreateOrderRequest`（下单请求）

Java 17 `record`，带 Jakarta Validation 注解，在 Controller 入参处用 `@Valid` 触发校验：

| 字段 | 校验 | 说明 |
| --- | --- | --- |
| `roomTypeId` | `@NotNull` | 房型 ID |
| `checkInDate` | `@NotNull` | 入住日期 |
| `checkOutDate` | `@NotNull` | 离店日期（先后顺序由 Service 校验） |
| `roomCount` | `@NotNull` `@Min(1)` `@Max(10)` | 1–10 间 |
| `contactName` | `@NotBlank` `@Size(max=50)` | 联系人 |
| `contactPhone` | `@NotBlank` `@Pattern("^1[3-9]\\d{9}$")` | 11 位大陆手机号 |
| `remark` | `@Size(max=255)` | 可选备注 |

### 6.2 `CancelRequest`（取消/拒绝原因）

只有一个可选字段 `reason`，`@Size(max=255)`。Controller 允许 `@RequestBody(required = false)`，所以不传 body 也能取消。

### 6.3 `OrderVO`（订单视图）

列表和详情都用它。比 `Order` 实体多了三个展示字段：

- `roomTypeName`：房型名称（关联查询补全）；
- `roomNos`：已分配房间号列表（`List<String>`）；
- `statusText`：状态中文文案，由 `OrderStatus.text()` 填充。

静态工厂 `from(Order, roomTypeName, roomNos)` 把实体转成视图，集中做映射，避免在 Controller 里散落转换代码。

### 6.4 `OrderDetailVO`（订单详情）

`record OrderDetailVO(OrderVO order, List<OrderLogVO> logs)`，把订单主体和按时间正序的状态日志打包返回。

### 6.5 `OrderLogVO`（日志视图）

在 `OrderLog` 基础上多了 `fromStatusText` 和 `toStatusText` 两个中文字段。`from()` 工厂里对 `fromStatus == null`（创建日志）做了判空，文案返回 `null` 而不是调用 `OrderStatus.text(null)`。

## 7. 数据访问层 mapper

四个 Mapper 都继承 `BaseMapper<T>`，开箱获得 `insert`、`updateById`、`selectById`、`selectPage`、`selectList`、`selectBatchIds` 等通用方法。它们本身没有自定义 SQL，自定义 SQL 在兄弟模块的 Mapper 里。

### 7.1 本模块的四个 Mapper

| Mapper | 继承 | 自定义方法 |
| --- | --- | --- |
| `OrderMapper` | `BaseMapper<Order>` | 无 |
| `OrderRoomMapper` | `BaseMapper<OrderRoom>` | 无（但 `order` 包外的查询会用到它，见下） |
| `OrderStayMapper` | `BaseMapper<OrderStay>` | 无 |
| `OrderLogMapper` | `BaseMapper<OrderLog>` | 无 |

> 实际上 `OrderRoomMapper` 的自定义 SQL 写在了 `order/mapper/OrderRoomMapper.java`，查询“区间内被有效订单占用的房间”。`OrderService` 大量用到它，见 8.7。

### 7.2 跨模块依赖的自定义 SQL

`OrderService` 下单时调用了另外两个模块 Mapper 的自定义方法，这些是订单能正确扣库存、分房的关键：

**`RoomCalendarMapper`（calendar 模块）：**

```java
// 原子扣减：只有开放且库存足够才会成功，靠影响行数判断是否抢到
@Update("UPDATE room_calendar SET stock = stock - #{count}, version = version + 1 " +
        "WHERE room_type_id = #{roomTypeId} AND stay_date = #{stayDate} AND status = 1 AND stock >= #{count}")
int decreaseStock(...);

// 取消归还库存
@Update("UPDATE room_calendar SET stock = stock + #{count}, version = version + 1 " +
        "WHERE room_type_id = #{roomTypeId} AND stay_date = #{stayDate}")
int increaseStock(...);
```

**`RoomMapper`（room 模块）：**

```java
// 加行锁读取该房型可用房间，避免并发分房冲突
@Select("SELECT * FROM room WHERE room_type_id = #{roomTypeId} AND status = 1 ORDER BY room_no FOR UPDATE")
List<Room> selectBookableRoomsForUpdate(...);
```

以及 `OrderRoomMapper` 自己的占用查询（见 8.7）。

## 8. 业务层 service：OrderService

文件：`order/service/OrderService.java`，约 400 行，是订单模块唯一有逻辑的类。下面按方法逐个讲解。

### 8.1 常量与依赖注入

```java
private static final int MAX_NIGHTS = 30;                              // 单次最多 30 晚
private static final DateTimeFormatter ORDER_NO_FORMAT =
        DateTimeFormatter.ofPattern("yyyyMMddHHmmss");                 // 订单号时间戳格式
```

构造器注入 7 个 Mapper：本模块 4 个 + `RoomTypeMapper`、`RoomMapper`、`RoomCalendarMapper`。用构造器注入而不是字段注入，便于测试和不可变。

### 8.2 `create` —— 下单（核心事务）

`@Transactional` 标注，整段方法在一个事务里。流程分 6 步：

**第 1 步：参数校验**

```java
if (checkIn.isBefore(LocalDate.now())) { throw ... "入住日期不能早于今天"; }
if (!checkOut.isAfter(checkIn))      { throw ... "离店日期必须晚于入住日期"; }
int nights = (int) ChronoUnit.DAYS.between(checkIn, checkOut);
if (nights > MAX_NIGHTS) { throw ... "单次最多预订 30 晚"; }
```

这里只校验日期合法性和最大晚数，`roomCount` 的 1–10 范围已由 DTO 注解保证。

**第 2 步：房型校验**

```java
RoomType roomType = roomTypeMapper.selectById(request.roomTypeId());
if (roomType == null || !Objects.equals(roomType.getStatus(), 1)) {
    throw new BizException(ErrorCode.NOT_FOUND, "房型不存在或已下架");
}
```

`status = 1` 表示上架。即使搜索时是上架的，下单瞬间也要再校验一次，防止期间被房东下架。

**第 3 步：逐晚校验日历并累计单价**

```java
List<LocalDate> dates = checkIn.datesUntil(checkOut).toList();   // [checkIn, checkOut) 的每晚
Map<LocalDate, RoomCalendar> calendarMap = calendarMapper.selectList(
        new LambdaQueryWrapper<RoomCalendar>()
                .eq(RoomCalendar::getRoomTypeId, request.roomTypeId())
                .between(RoomCalendar::getStayDate, checkIn, checkOut.minusDays(1)))
        .stream().collect(Collectors.toMap(RoomCalendar::getStayDate, Function.identity()));
```

一次 SQL 把区间内所有日历行查出来转成 `Map<日期, 日历>`，避免逐晚查询。然后循环每晚：

```java
for (LocalDate date : dates) {
    RoomCalendar calendar = calendarMap.get(date);
    if (calendar == null)                       throw "未开放预订";
    if (!Objects.equals(calendar.getStatus(), 1)) throw "已关房";
    if (calendar.getStock() < request.roomCount()) throw "库存不足，仅剩 N 间";
    nightTotal = nightTotal.add(calendar.getPrice());   // 累加单间总价
}
```

`nightTotal` 是**一间房**住完整段的价格，最后乘间数才是订单总额。

**第 4 步：原子扣减库存**

```java
for (LocalDate date : dates) {
    if (calendarMapper.decreaseStock(request.roomTypeId(), date, request.roomCount()) != 1) {
        throw new BizException(ErrorCode.CONFLICT, "库存不足，请重新选择日期");
    }
}
```

这一步是并发安全的关键：把 `stock >= count` 写进 `WHERE`，靠数据库行锁保证原子性。影响行数不为 1（可能是 0 或多行，但唯一键保证最多 1 行）就说明被别的订单抢走，抛异常回滚。

注意：**扣减发生在选房之前**。如果后面选房失败，整个事务回滚，已扣的库存也会还原，不会留下“扣了库存却没订单”的脏状态。

**第 5 步：分配物理房间**

```java
List<Room> assignedRooms = allocateRooms(request.roomTypeId(), checkIn, checkOut, request.roomCount());
```

`allocateRooms` 是私有方法（见 8.7），返回连续整段日期都空闲的房间。凑不出就抛异常回滚，**不做房号重排**。

**第 6 步：落库 4 张表**

```java
Order order = new Order();
order.setOrderNo(generateOrderNo());
order.setTotalAmount(nightTotal.multiply(BigDecimal.valueOf(request.roomCount())));
order.setStatus(OrderStatus.PENDING);
// ... 其余字段
orderMapper.insert(order);
order.setCreatedAt(LocalDateTime.now());   // DB 默认值不回填，手动补时间供响应使用

for (Room room : assignedRooms) {          // order_room：分到哪些房间
    OrderRoom link = new OrderRoom();
    link.setOrderId(order.getId());
    link.setRoomId(room.getId());
    orderRoomMapper.insert(link);
}
for (LocalDate date : dates) {              // order_stay：占了哪几晚
    OrderStay stay = new OrderStay();
    stay.setOrderId(order.getId());
    stay.setStayDate(date);
    orderStayMapper.insert(stay);
}
addLog(order.getId(), null, OrderStatus.PENDING, userId, "房客提交订单");  // order_log
```

写入顺序：`orders` → `order_room` → `order_stay` → `order_log`。因为 `order_room`/`order_stay` 需要 `order.getId()`（自增主键，insert 后回填），所以必须先插主单。

最后返回 `OrderVO.from(order, roomType.getName(), roomNos)`。

### 8.3 `myOrders` —— 房客查自己的订单

```java
public PageResult<OrderVO> myOrders(Long userId, String status, long page, long size) {
    LambdaQueryWrapper<Order> wrapper = new LambdaQueryWrapper<Order>()
            .eq(Order::getUserId, userId)
            .eq(StringUtils.hasText(status), Order::getStatus, status)   // 状态非空才加条件
            .orderByDesc(Order::getId);
    return toPage(orderMapper.selectPage(new Page<>(page, size), wrapper));
}
```

按 `userId` 过滤，状态可选，按 id 倒序（新单在前）。`toPage` 统一补全房型名和房间号（见 8.10）。

### 8.4 `page` —— 房东查全部订单

```java
LambdaQueryWrapper<Order> wrapper = new LambdaQueryWrapper<Order>()
        .eq(StringUtils.hasText(status), Order::getStatus, status)
        .and(StringUtils.hasText(keyword), query -> query
                .like(Order::getOrderNo, keyword).or().like(Order::getContactPhone, keyword))
        .orderByDesc(Order::getId);
```

没有 `userId` 过滤（房东看全部），`keyword` 支持订单号或联系电话模糊搜索，两个条件用 `OR` 包在 `.and(...)` 里，避免和状态条件的优先级混乱。

### 8.5 `detail` —— 订单详情（含日志）

```java
public OrderDetailVO detail(Long orderId, Long userId, boolean admin) {
    Order order = getExisting(orderId);
    if (!admin && !Objects.equals(order.getUserId(), userId)) {
        throw new BizException(ErrorCode.NOT_FOUND, "订单不存在");   // 越权查别人的订单，返回“不存在”避免泄露
    }
    List<OrderLogVO> logs = orderLogMapper.selectList(
            new LambdaQueryWrapper<OrderLog>().eq(OrderLog::getOrderId, orderId)
                    .orderByAsc(OrderLog::getId))                    // 日志按时间正序
            .stream().map(OrderLogVO::from).toList();
    return new OrderDetailVO(OrderVO.from(order, roomTypeName(...), loadRoomNos(orderId)), logs);
}
```

`admin` 参数区分调用来源：房东端传 `true` 可看任意单，房客端传 `false` 只能看自己的。越权时不抛“无权限”而抛“订单不存在”，避免攻击者通过报错判断订单是否存在。

### 8.6 `cancelByCustomer` —— 房客取消

```java
public OrderVO cancelByCustomer(Long orderId, Long userId, String reason) {
    Order order = getExisting(orderId);
    if (!Objects.equals(order.getUserId(), userId)) { throw "订单不存在"; }
    return cancelInternal(order, userId, StringUtils.hasText(reason) ? reason : "房客取消订单");
}
```

先校验归属，再委托给 `cancelInternal`。默认原因“房客取消订单”。

### 8.7 `allocateRooms` —— 分配房间（私有，关键并发逻辑）

```java
private List<Room> allocateRooms(Long roomTypeId, LocalDate checkIn, LocalDate checkOut, int roomCount) {
    List<Room> candidates = roomMapper.selectBookableRoomsForUpdate(roomTypeId);   // FOR UPDATE 行锁
    if (candidates.isEmpty()) throw "该房型暂无可用房间";

    Set<Long> occupied = new HashSet<>(orderRoomMapper.selectOccupiedRoomIds(roomTypeId, checkIn, checkOut));
    List<Room> free = candidates.stream().filter(r -> !occupied.contains(r.getId())).toList();
    if (free.size() < roomCount) {
        throw "所选日期每晚虽有余量，但没有同一间房可连续入住整段日期...";
    }
    return free.subList(0, roomCount);
}
```

三步：

1. `selectBookableRoomsForUpdate` 用 `FOR UPDATE` 锁住该房型所有可用房间的行，防止并发下单时两单同时选到同一间房；
2. `selectOccupiedRoomIds` 查出区间内被有效订单（`PENDING/CONFIRMED/CHECKED_IN/COMPLETED`）占用的房间 ID，注意这里**包含 `COMPLETED`**——已完成的订单日期都在过去，不会影响未来预订，但统一过滤更安全；
3. 用 `occupied` 集合过滤出真正空闲的房间，数量够就取前 `roomCount` 间，不够直接拒绝。

`selectOccupiedRoomIds` 的日期重叠判断用半开区间：

```sql
o.check_in_date < #{checkOut} AND o.check_out_date > #{checkIn}
```

这保证前一单离店当天可以接下一单入住（离店日不含、入住日含）。

> **不重排原则**：已有订单分到的房间不会被挪动去腾挪给新单。如果连续房间凑不够，直接拒绝下单，而不是尝试重排。这样实现简单，也避免了“已确认订单房号被偷偷换掉”的体验问题。

### 8.8 `cancelInternal` —— 取消/拒绝共用逻辑

`cancelByCustomer` 和 `reject` 都走这里：

```java
private OrderVO cancelInternal(Order order, Long operatorId, String reason) {
    if (!OrderStatus.canTransition(order.getStatus(), OrderStatus.CANCELLED)) {
        throw "订单当前状态为「...」，不能取消";
    }
    Order update = new Order();
    update.setId(order.getId());
    update.setStatus(OrderStatus.CANCELLED);
    update.setCancelReason(reason);
    orderMapper.updateById(update);                          // 局部更新，只改 status 和 cancel_reason

    List<OrderStay> stays = orderStayMapper.selectList(
            new LambdaQueryWrapper<OrderStay>().eq(OrderStay::getOrderId, order.getId()));
    for (OrderStay stay : stays) {
        calendarMapper.increaseStock(order.getRoomTypeId(), stay.getStayDate(), order.getRoomCount());
    }
    addLog(order.getId(), order.getStatus(), OrderStatus.CANCELLED, operatorId, reason);
    order.setStatus(OrderStatus.CANCELLED);
    order.setCancelReason(reason);
    return OrderVO.from(...);
}
```

关键点：

- **先校验状态机**，只有 `PENDING`/`CONFIRMED` 能取消；
- 用 `new Order()` + `setId` + `updateById` 做**局部更新**，只改 `status` 和 `cancel_reason`，不会把实体里其他字段（如 `null` 的 `createdAt`）覆盖掉；
- 归还库存严格按 `order_stay` 的每一晚执行 `stock + roomCount`，和下单时的扣减一一对应；
- `order_room` 记录**不删除**，保留历史房号；但占用查询只统计未取消状态，所以房间会自然释放。

### 8.9 `confirm` / `reject` / `checkIn` / `complete` —— 房东操作

四个方法都很薄：

```java
public OrderVO confirm(Long orderId, Long operatorId) {
    return transition(orderId, OrderStatus.CONFIRMED, operatorId, "房东确认订单");
}
public OrderVO checkIn(Long orderId, Long operatorId) {
    return transition(orderId, OrderStatus.CHECKED_IN, operatorId, "房客入住");
}
public OrderVO complete(Long orderId, Long operatorId) {
    return transition(orderId, OrderStatus.COMPLETED, operatorId, "订单完成");
}
```

`reject` 单独处理，因为它要归还库存：

```java
public OrderVO reject(Long orderId, Long operatorId, String reason) {
    Order order = getExisting(orderId);
    if (!OrderStatus.canTransition(order.getStatus(), OrderStatus.CANCELLED)) { throw ...; }
    return cancelInternal(order, operatorId, StringUtils.hasText(reason) ? reason : "房东拒绝订单");
}
```

`transition` 私有方法做前向流转：

```java
private OrderVO transition(Long orderId, String toStatus, Long operatorId, String remark) {
    Order order = getExisting(orderId);
    if (!OrderStatus.canTransition(order.getStatus(), toStatus)) { throw ...; }
    Order update = new Order();
    update.setId(orderId);
    update.setStatus(toStatus);
    orderMapper.updateById(update);
    addLog(orderId, order.getStatus(), toStatus, operatorId, remark);
    order.setStatus(toStatus);
    return OrderVO.from(...);
}
```

确认、入住、完成**都不碰库存**——库存只在下单和取消两个时点变化。

### 8.10 `toPage` —— 分页结果转视图（N+1 优化）

```java
private PageResult<OrderVO> toPage(Page<Order> result) {
    List<Long> typeIds = result.getRecords().stream().map(Order::getRoomTypeId).distinct().toList();
    Map<Long, String> typeNames = typeIds.isEmpty() ? Map.of()
            : roomTypeMapper.selectBatchIds(typeIds).stream()
                    .collect(Collectors.toMap(RoomType::getId, RoomType::getName));
    Map<Long, List<String>> roomNosByOrder = loadRoomNosBatch(result.getRecords());
    List<OrderVO> records = result.getRecords().stream()
            .map(o -> OrderVO.from(o, typeNames.get(o.getRoomTypeId()),
                    roomNosByOrder.getOrDefault(o.getId(), List.of())))
            .toList();
    return PageResult.of(records, result.getTotal(), result.getCurrent(), result.getSize());
}
```

如果分页 10 条订单，逐条查房型名和房间号会产生 20+ 次查询。这里用 `selectBatchIds` 一次查出所有房型名，用 `loadRoomNosBatch` 一次查出所有订单的房间号，把查询数压到常数级。

### 8.11 其他私有辅助方法

- `addLog`：插入一条 `OrderLog`，`fromStatus` 为创建时传 `null`；
- `loadRoomNos(orderId)`：查单个订单的房间号并按房号排序；
- `loadRoomNosBatch(orders)`：批量查多单的房间号，按订单分组，组内排序（见 8.10）；
- `getExisting(orderId)`：按 id 查订单，不存在抛 `NOT_FOUND`；
- `roomTypeName(roomTypeId)`：查房型名，不存在返回 `null`（不抛异常，因为历史订单可能房型已被删）；
- `generateOrderNo()`：生成 `HS + yyyyMMddHHmmss + 4位随机数` 格式的订单号。

```java
private String generateOrderNo() {
    return "HS" + LocalDateTime.now().format(ORDER_NO_FORMAT)
            + String.format("%04d", ThreadLocalRandom.current().nextInt(10000));
}
```

用 `ThreadLocalRandom` 而不是 `Math.random`，并发下性能更好。订单号有数据库唯一约束兜底，极小概率撞号会让 insert 失败回滚，房客重试即可。

### 9.1 `OrderController`（房客端）

private Long userId(Authentication authentication) {

`LoginUser` 是 `security` 模块定义的 `record`，在 `JwtAuthenticationFilter` 解析 token 后放进 `SecurityContext`。

## 10. 核心流程时序图

### 10.1 下单流程

```
房客前端          OrderController        OrderService         DB(4表+calendar+room)
   │  POST /api/orders                    │                     │
   │ ──────────────────►                  │                     │
   │                                      │ create()            │
   │                                      ├─ 校验日期/房型       │
   │                                      ├─ 查日历 map         │ SELECT ... room_calendar
   │                                      ├─ 逐晚校验库存        │                     │
   │                                      ├─ 逐晚扣减 stock ────┼──► UPDATE (原子)     │
   │                                      ├─ FOR UPDATE 选房 ───┼──► SELECT ... room   │
   │                                      │   (凑不出则回滚)     │                     │
   │                                      ├─ INSERT orders ─────┼──►                   │
   │                                      ├─ INSERT order_room ─┼──►                   │
   │                                      ├─ INSERT order_stay ─┼──►                   │
   │                                      ├─ INSERT order_log ──┼──►                   │
   │                                      │ return OrderVO      │
   │ ◄────────────────── 200 OK           │                     │
```

整个 `create` 方法在一个 `@Transactional` 事务里，任何一步抛异常全部回滚。

### 10.2 取消/拒绝流程

```
cancelByCustomer / reject
        │
        ├─ getExisting + 校验归属/状态机
        ├─ update orders SET status=CANCELLED, cancel_reason
        ├─ SELECT order_stay (这单占了哪几晚)
        ├─ 逐晚 UPDATE room_calendar SET stock = stock + roomCount
        ├─ INSERT order_log (from → CANCELLED)
        └─ return OrderVO
```

### 10.3 状态流转（确认/入住/完成）

```
confirm / checkIn / complete
        │
        ├─ getExisting
        ├─ OrderStatus.canTransition 校验
        ├─ update orders SET status = 新状态
        ├─ INSERT order_log
        └─ return OrderVO
```

不碰库存、不碰房间。

## 11. 关键设计点

### 11.1 半开区间 `[checkIn, checkOut)`

全模块统一：入住日含、离店日不含。好处是前一单离店当天可接下一单入住，不会因为“同一天算两晚”少卖房。`order_stay` 也是按这个区间生成的。

### 11.2 两本账：库存 vs 房间分配

- `room_calendar.stock` 是“还能卖几间”；
- `order_room` 是“哪些物理房间被占了”。

搜索和报价取两者较小值，下单时两本账都再校验。这样能发现“日历还有库存，但连续房间排不开”的情况（例如周末只剩零散房间，没法连住 3 晚）。

### 11.3 并发安全

- **扣库存**：条件 UPDATE `WHERE stock >= n`，原子性由数据库行锁保证；
- **分房**：`SELECT ... FOR UPDATE` 锁住候选房间，避免两单分同一间；
- **唯一键兜底**：`orders.order_no` 唯一、`order_room(order_id, room_id)` 唯一、`room_calendar(room_type_id, stay_date)` 唯一。

### 11.4 事务边界

`create`、`cancelByCustomer`、`reject`、`confirm`、`checkIn`、`complete` 都标了 `@Transactional`。库存扣减 + 房间分配 + 订单落库要么全成功要么全失败。

### 11.5 不重排已有订单

`allocateRooms` 凑不出连续房间就拒绝，不会挪动已确认订单的房号。这是一个刻意的简化：实现简单，且避免“房东/房客看到的房号被偷偷改掉”。

### 11.6 越权防护

房客端查详情/取消时，`userId` 从登录态取，不接受前端传参；越权访问返回“订单不存在”而非“无权限”，避免信息泄露。

### 11.7 N+1 查询优化

列表页用 `selectBatchIds` 批量补全房型名和房间号，而不是每条订单单独查。

## 12. 边界与可改进点

这些是当前实现的已知边界，生产化时可以考虑补强：

1. **无幂等键**：防重复下单靠前端按钮禁用 + 后端状态校验。极端网络重试可能产生重复订单，可加请求号唯一约束或幂等表。
2. **日历库存是快照**：`batchInsertIgnore` 生成日历时把当时可用房间数写入 `stock`，之后新增房间不会自动补到已生成的日期，需要房东手动改库存或重新生成。
3. **不支持改期**：目前只能取消后重新下单。改期需要“旧日期归还 + 新日期扣减 + 房号重算”在一个事务里完成，是单独的流程。
4. **未接支付**：`total_amount` 只是快照金额，没有支付流水，`PENDING` 直接由房东确认。适合演示，不适合真实交易。
5. **订单号撞号靠唯一键兜底**：高并发下 `HS + 时间戳 + 4 位随机` 有极小概率撞号，可改为更短的雪花 ID 或加数据库序列。
6. **无外键约束**：引用完整性靠应用层校验，删除房型/房间时没有级联保护（`RoomTypeService.delete` 会先检查是否有房间，但 `orders` 不阻止删除历史房型）。
7. **`order_room` 取消后不清理**：保留记录用于历史展示，依赖占用查询过滤 `CANCELLED`。如果数据量大，可考虑归档。
