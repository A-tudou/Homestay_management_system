## 1. 模块概览

房间模块维护的是**物理房间**——也就是实际可以入住的那一间间房。它和 `roomtype` 模块是“一对多”关系：一个房型（如山景大床房）下可以有多间物理房间（如 201、202、203）。

这个模块的职责很纯粹：**房东端对物理房间做增删改查和状态切换**。它本身不参与价格和库存计算，但它提供的两个查询能力是整个预订系统能正确分房的关键：

- 下单时用 `FOR UPDATE` 锁住可用房间，避免并发分房冲突；
- 搜索时统计某段日期内连续空闲的房间数，避免“显示可订但实际凑不出连续房间”。

模块只暴露房东端接口 `/api/admin/rooms`，房客端不直接访问房间表——房客看到的是房型和房态，具体分到哪间房由后端在下单时决定。

## 3. 数据表设计

`room` 表在 `src/main/resources/db/schema.sql` 中定义：

```sql
CREATE TABLE IF NOT EXISTS room (
    id           BIGINT      NOT NULL AUTO_INCREMENT,
    room_type_id BIGINT      NOT NULL COMMENT '所属房型',
    room_no      VARCHAR(20) NOT NULL COMMENT '房间号，如 201',
    floor        INT         DEFAULT NULL COMMENT '楼层',
    status       TINYINT     NOT NULL DEFAULT 1 COMMENT '1 可用 0 维修中',
    created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_room_no (room_no),
    KEY idx_room_type (room_type_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '物理房间';
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增主键 |
| `room_type_id` | BIGINT | 所属房型 ID（无外键，应用层校验存在性） |
| `room_no` | VARCHAR(20) | 房间号，**全局唯一**，如 `201`、`A-101` |
| `floor` | INT | 楼层，可空，允许负值（地下层） |
| `status` | TINYINT | `1` 可用 / `0` 维修中，默认 `1` |
| `created_at` / `updated_at` | DATETIME | 创建 / 更新时间（DB 默认值自动维护） |

两个索引的用途：

- `uk_room_no (room_no)`：保证房间号全局唯一，数据库层面兜底，即使应用层查重有并发漏洞也不会插入重复房间号；
- `idx_room_type (room_type_id)`：服务按“查某房型下所有房间”的高频查询建的索引，下单选房和列表过滤都会用到。

> 和系统其它表一样，`room` 表没有定义数据库外键，引用完整性由 `RoomService` 在写操作前校验。

## 4. 实体层 entity：Room

文件：`room/entity/Room.java`

纯 POJO，用 MyBatis-Plus 注解映射：

```java
@TableName("room")
public class Room {
    @TableId(type = IdType.AUTO)
    private Long id;
    private Long roomTypeId;
    private String roomNo;
    private Integer floor;
    private Integer status;
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
    // 标准 getter/setter ...
}
```

类注释明确了两个关键约定：

1. 物理房间归属于某个房型，同一房型下可有多间；
2. `status` 取值 `1` 可用 / `0` 维修中，**维修中的房间不参与下单分配**。

这一点很重要：维修状态不是软删除，房间记录保留（历史订单的 `order_room` 仍引用它），只是在选房 SQL 里被 `status = 1` 过滤掉。

## 5. 数据传输层 dto

### 5.1 `RoomRequest`（新增/修改请求）

Java 17 `record`，带 Jakarta Validation 注解，在 Controller 入参处用 `@Valid` 触发校验：

| 字段 | 校验 | 说明 |
| --- | --- | --- |
| `roomTypeId` | `@NotNull` | 所属房型 ID |
| `roomNo` | `@NotBlank` `@Pattern("^[A-Za-z0-9-]{1,20}$")` | 字母、数字或短横线，最长 20 位，全局唯一 |
| `floor` | `@Min(-5)` `@Max(200)` | 楼层，允许 -5 到 200（含地下层） |

注意：请求里**没有 `status` 字段**——新增时状态由 Service 强制设为 `1`（可用），修改状态走单独的 `PATCH /{id}/status` 接口。这样把“编辑房间信息”和“切换可用/维修”两个动作解耦，避免误改状态。

### 5.2 `RoomVO`（房间视图）

列表和详情都用它，比实体多了一个 `roomTypeName` 字段：

```java
public record RoomVO(
        Long id, Long roomTypeId, String roomTypeName,
        String roomNo, Integer floor, Integer status, LocalDateTime createdAt
) {}
```

`roomTypeName` 不是 `room` 表的字段，是 Service 层关联 `room_type` 表查出来补全的，方便列表直接展示“这是哪个房型的房间”。`RoomVO` 没有静态 `from` 工厂，转换逻辑放在 `RoomService.toVO` 私有方法里。

### 5.3 `RoomFreeStat`（空闲房间统计结果）

```java
public class RoomFreeStat {
    private Long roomTypeId;
    private Integer freeRooms;
    // getter/setter
}
```

这是一个**查询结果载体**，不对应任何表。它承接 `RoomMapper.selectFreeRoomStats` 的返回——“某房型在整段入住区间内都空闲的物理房间数”，用于搜索时判断房型能否连续入住。用普通类（不是 record）是因为 MyBatis 默认通过 setter 注入查询结果，record 的不可变特性会让映射麻烦，所以这里用了带 setter 的普通类。

## 6. 数据访问层 mapper：RoomMapper

文件：`room/mapper/RoomMapper.java`

继承 `BaseMapper<Room>` 获得通用 CRUD，另外定义了 3 个自定义查询，全部分配房和搜索场景服务。

### 6.1 `selectBookableRoomsForUpdate` —— 下单选房（行锁）

```java
@Select("SELECT * FROM room WHERE room_type_id = #{roomTypeId} AND status = 1 ORDER BY room_no FOR UPDATE")
List<Room> selectBookableRoomsForUpdate(@Param("roomTypeId") Long roomTypeId);
```

下单时由 `OrderService.allocateRooms` 调用。关键点：

- `FOR UPDATE` 给查出的行加**排他锁**，在事务提交前其它事务不能修改这些行，避免两个并发订单同时选中同一间房；
- `status = 1` 只选可用房间，维修中的直接排除；
- `ORDER BY room_no` 让分配结果稳定（总是从房号小的开始分），也减少死锁概率——所有事务都按相同顺序加锁。

### 6.2 `selectBookableRoomIds` —— 只读查可用房间 ID

```java
@Select("SELECT id FROM room WHERE room_type_id = #{roomTypeId} AND status = 1")
List<Long> selectBookableRoomIds(@Param("roomTypeId") Long roomTypeId);
```

不加锁的版本，供房客侧核算连续可订间数时使用（`CalendarService` 报价逻辑会用到）。只查 `id` 不查整行，减少数据传输。

### 6.3 `selectFreeRoomStats` —— 整段区间空闲房间统计

```java
@Select("SELECT r.room_type_id AS roomTypeId, COUNT(*) AS freeRooms FROM room r " +
        "WHERE r.status = 1 AND NOT EXISTS (" +
        "  SELECT 1 FROM order_room om JOIN orders o ON o.id = om.order_id " +
        "  WHERE om.room_id = r.id " +
        "  AND o.status IN ('PENDING', 'CONFIRMED', 'CHECKED_IN', 'COMPLETED') " +
        "  AND o.check_in_date < #{checkOut} AND o.check_out_date > #{checkIn}) " +
        "GROUP BY r.room_type_id HAVING COUNT(*) >= #{roomCount}")
List<RoomFreeStat> selectFreeRoomStats(...);
```

这是搜索时的**第二层过滤**（第一层是 `room_calendar` 的库存过滤，见订单模块文档）。逻辑：

- 外层查所有 `status = 1` 的可用房间；
- 用 `NOT EXISTS` 关联子查询排除那些在 `[checkIn, checkOut)` 区间内被有效订单占用的房间；
- 有效订单状态是 `PENDING / CONFIRMED / CHECKED_IN / COMPLETED`——注意包含 `COMPLETED`，因为已完成订单的入住日期在过去，不影响未来预订，统一过滤更安全；已取消订单自然不在其中，房间已释放；
- 日期重叠判断用半开区间：`o.check_in_date < checkOut AND o.check_out_date > checkIn`，前一单离店当天可接下一单入住；
- `GROUP BY room_type_id HAVING COUNT(*) >= roomCount`——只保留连续空闲房间数 ≥ 预订间数的房型。

这一条 SQL 保证了搜索结果和真实分房规则一致：不会出现“搜索显示可订，但下单时凑不出连续房间”的尴尬。

## 7. 业务层 service：RoomService

文件：`room/service/RoomService.java`，约 160 行。房东端管理物理房间的全部逻辑都在这里。

### 7.1 依赖注入

```java
private final RoomMapper roomMapper;
private final RoomTypeMapper roomTypeMapper;
```

只依赖本模块的 `RoomMapper` 和房型模块的 `RoomTypeMapper`——后者用于校验房型是否存在、补全房型名称。**不依赖订单和日历模块**，依赖方向是单向的（订单/日历依赖 room，room 不依赖它们）。

### 7.2 `create` —— 新增房间

```java
@Transactional
public RoomVO create(RoomRequest request) {
    ensureRoomTypeExists(request.roomTypeId());     // 房型必须存在
    ensureRoomNoAvailable(request.roomNo(), null);   // 房间号不能重复
    Room room = new Room();
    applyRequest(room, request);
    room.setStatus(1);                                // 新增房间默认可用
    roomMapper.insert(room);
    return toVO(room, getRoomTypeName(request.roomTypeId()));
}
```

两步校验后写入，状态强制 `1`。`@Transactional` 虽然这里只有一次 insert，但加上是为了和其它写方法保持一致的事务语义，未来若加关联操作也不会漏。

### 7.3 `update` —— 修改房间

```java
@Transactional
public RoomVO update(Long id, RoomRequest request) {
    Room room = getExisting(id);
    ensureRoomTypeExists(request.roomTypeId());
    ensureRoomNoAvailable(request.roomNo(), id);     // 查重时排除自身
    applyRequest(room, request);
    roomMapper.updateById(room);
    return toVO(roomMapper.selectById(id), getRoomTypeName(request.roomTypeId()));
}
```

和 `create` 的区别：

- 先 `getExisting` 确认房间存在；
- `ensureRoomNoAvailable` 传入 `excludeId = id`，修改房号时不会把自己算作冲突；
- 返回值重新 `selectById` 而不是用传入的 `room`，因为 `updateById` 后 `room` 对象里 `updatedAt` 等字段不是最新的（DB 自动维护），重查一次拿到完整数据。

允许修改所属房型——也就是说一间房可以从“山景大床房”挪到“海景大床房”。但要注意：挪房型不会自动迁移该房间的历史订单关联，历史订单仍按原 `room_type_id` 统计。

### 7.4 `updateStatus` —— 切换可用/维修

```java
@Transactional
public void updateStatus(Long id, Integer status) {
    getExisting(id);
    Room update = new Room();
    update.setId(id);
    update.setStatus(status);
    roomMapper.updateById(update);
}
```

用 `new Room()` + `setId` + `updateById` 做**局部更新**，只改 `status` 一列，不会覆盖其它字段。没有校验 `status` 只能是 0/1，这个校验放在 `StatusRequest` 的注解或前端，但 Service 层没兜底——这是一个可以加强的点（见第 11 节）。

### 7.5 `delete` —— 删除房间

```java
@Transactional
public void delete(Long id) {
    getExisting(id);
    roomMapper.deleteById(id);
}
```

只校验存在性就直接删。类注释说明：**历史订单通过 `order_room` 保留房间 ID 引用**，所以删除房间不会导致历史订单丢失房号展示（`order_room.room_id` 还在，只是查房间详情时可能查不到）。

这里没有检查“房间是否被未完成订单占用”就允许删除，是一个风险点——详见第 11 节。

### 7.6 `page` —— 分页查询

```java
public PageResult<RoomVO> page(long page, long size, Long roomTypeId, Integer status) {
    LambdaQueryWrapper<Room> wrapper = new LambdaQueryWrapper<Room>()
            .eq(roomTypeId != null, Room::getRoomTypeId, roomTypeId)
            .eq(status != null, Room::getStatus, status)
            .orderByAsc(Room::getRoomTypeId)
            .orderByAsc(Room::getRoomNo);
    Page<Room> result = roomMapper.selectPage(new Page<>(page, size), wrapper);
    Map<Long, String> typeNames = loadRoomTypeNames(result.getRecords());
    List<RoomVO> records = result.getRecords().stream()
            .map(room -> toVO(room, typeNames.get(room.getRoomTypeId())))
            .toList();
    return PageResult.of(records, result.getTotal(), result.getCurrent(), result.getSize());
}
```

- `roomTypeId` 和 `status` 都是可选过滤条件，用 MyBatis-Plus 的条件构造器 `.eq(条件, 字段, 值)` 动态拼接；
- 排序按 `roomTypeId` 再按 `roomNo`，让列表按房型分组、房号升序展示；
- 房型名称用 `loadRoomTypeNames` **批量查询**（`selectBatchIds`），避免分页 10 条就查 10 次房型表的 N+1 问题。

### 7.7 `get` —— 房间详情

```java
public RoomVO get(Long id) {
    Room room = getExisting(id);
    return toVO(room, getRoomTypeName(room.getRoomTypeId()));
}
```

单条查询，直接查一次房型名。

### 7.8 私有辅助方法

| 方法 | 作用 |
| --- | --- |
| `loadRoomTypeNames(List<Room>)` | 批量查分页结果涉及的房型名，返回 `Map<roomTypeId, name>`，N+1 优化 |
| `getRoomTypeName(Long)` | 查单个房型名，房型不存在返回 `null`（历史房间可能房型已删） |
| `getExisting(Long)` | 按 id 查房间，不存在抛 `NOT_FOUND` 业务异常 |
| `ensureRoomTypeExists(Long)` | 校验房型存在，不存在抛 `NOT_FOUND` |
| `ensureRoomNoAvailable(String, Long)` | 校验房间号唯一，`excludeId` 用于修改时排除自身，冲突抛 `CONFLICT` |
| `applyRequest(Room, RoomRequest)` | 把请求参数写入实体（房型、房号、楼层），不碰 status |
| `toVO(Room, String)` | 实体 + 房型名 → `RoomVO` |

`ensureRoomNoAvailable` 的查重实现：

```java
Long count = roomMapper.selectCount(new LambdaQueryWrapper<Room>()
        .eq(Room::getRoomNo, roomNo)
        .ne(excludeId != null, Room::getId, excludeId));
if (count > 0) { throw new BizException(ErrorCode.CONFLICT, "房间号 " + roomNo + " 已存在"); }
```

应用层查重 + 数据库唯一键双层保护。极端并发下两个请求同时通过应用层查重，唯一键会让其中一个 insert 失败抛异常，由全局异常处理器转成友好提示。

## 8. 控制层 controller：AdminRoomController

文件：`room/controller/AdminRoomController.java`

路径前缀 `/api/admin/rooms`，`/api/admin/**` 由 `SecurityConfig` 统一限制为 `HOST` 角色，Controller 内不再写鉴权代码。6 个端点：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/admin/rooms` | 新增房间，body 为 `RoomRequest` |
| `PUT` | `/api/admin/rooms/{id}` | 修改房间信息（房型/房号/楼层） |
| `PATCH` | `/api/admin/rooms/{id}/status` | 设为可用或维修中，body 为 `StatusRequest` |
| `DELETE` | `/api/admin/rooms/{id}` | 删除房间 |
| `GET` | `/api/admin/rooms/{id}` | 房间详情 |
| `GET` | `/api/admin/rooms?page=&size=&roomTypeId=&status=` | 分页列表，房型和状态可选过滤 |

接口设计上的两个考量：

- **修改信息**和**切换状态**分成 `PUT` 和 `PATCH` 两个接口，语义清晰，也避免前端编辑表单时误把状态改掉；
- `status` 切换用 `PATCH` 而非 `PUT`，符合 RESTful 中“局部更新”的语义，body 用通用的 `StatusRequest`（`record StatusRequest(Integer status)`），和房型、日历的状态切换复用同一个 DTO。

## 9. 跨模块协作：谁在调用 room

room 模块本身只做管理，但它的查询能力被三个模块依赖：

```
                    ┌──────────────────┐
                    │   room 模块      │
                    │  RoomMapper      │
                    └────────┬─────────┘
                             │ 被调用
          ┌──────────────────┼──────────────────┐
          ▼                  ▼                  ▼
   ┌────────────┐    ┌──────────────┐   ┌──────────────┐
   │  order     │    │  calendar    │   │  roomtype    │
   │ 模块       │    │ 模块         │   │ 模块         │
   └────────────┘    └──────────────┘   └──────────────┘
```

- **order 模块**（`OrderService`）：下单时调 `selectBookableRoomsForUpdate` 加行锁选房，调 `OrderRoomMapper`（关联查询）查占用房间；列表/详情补全房号时调 `roomMapper.selectBatchIds`。
- **calendar 模块**（`CalendarService`）：报价时调 `selectBookableRoomIds` 核算连续可订间数。
- **roomtype 模块**（`PublicRoomTypeService`）：搜索时调 `selectFreeRoomStats` 做第二层过滤；`RoomTypeService.delete` 会先查某房型下是否有房间，有则禁止删除。
- **config**（`DemoDataSeeder`）：演示数据生成时批量插入房间。

依赖方向是单向的：**room 不依赖 order/calendar**，只依赖 roomtype（校验房型存在）。这样 room 模块可以独立测试，不会被订单逻辑牵连。

## 10. 关键设计点

### 10.1 房型与物理房间分离

`room_type` 是“卖什么”（售卖单位，定价格/人数/床型），`room` 是“有什么”（物理库存）。分离后：

- 一个房型可以对应多间房，库存自然就是房间数；
- 价格按房型+日期存在 `room_calendar`，不需要每间房单独定价；
- 房东管理时，房型管“商品信息”，房间管“实物库存”，职责清晰。

### 10.2 维修状态而非软删除

`status = 0` 表示维修中，房间记录不删除。好处：

- 历史订单的 `order_room` 引用不失效；
- 维修结束直接改回 `status = 1` 即可恢复，不需要重建记录；
- 选房 SQL 统一加 `status = 1` 过滤，逻辑简单。

### 10.3 行锁选房防并发

`selectBookableRoomsForUpdate` 的 `FOR UPDATE` + `ORDER BY room_no` 是并发分房正确性的关键。所有下单事务按相同顺序（房号升序）对相同行加锁，避免死锁；锁在事务提交后释放，保证同一间房不会被两个订单同时分到。

### 10.4 搜索与分房规则一致

`selectFreeRoomStats` 的过滤条件和 `OrderService.allocateRooms` 的分房条件完全对齐（都排除有效订单占用、都用半开区间），保证搜索结果可订就一定能下单成功（库存层面的并发竞争除外）。

### 10.5 N+1 优化

列表页用 `selectBatchIds` 批量补全房型名，而不是每条房间查一次房型。这是 MyBatis-Plus 项目的标准优化手法。

### 10.6 应用层 + 数据库双层唯一约束

房间号唯一性既在 Service 层查重（给友好提示），又在数据库建唯一键（兜底防并发）。两层缺一不可：只靠应用层有并发漏洞，只靠数据库用户体验差。

## 11. 边界与可改进点

1. **`updateStatus` 不校验状态值**：Service 层没有限制 `status` 只能是 0 或 1，传 2 也会写进库。虽然 `StatusRequest` 和前端可能做了校验，但 Service 作为最后一道防线应加 `if (status != 0 && status != 1) throw ...`。

2. **删除房间不检查占用**：`delete` 只校验存在性就删。如果房间正被未完成订单（`PENDING/CONFIRMED/CHECKED_IN`）占用，删除后该订单的房号展示会受影响。建议删除前查 `order_room` 是否有有效订单引用，有则禁止删除。

3. **修改房型不迁移历史订单**：`update` 允许改 `roomTypeId`，但历史订单仍按原房型统计。如果业务要求“房间归属变更后历史订单也跟着变”，需要额外处理；当前实现是“历史不变，只影响未来”。

4. **`floor` 可空但无默认值**：DB 里 `floor` 允许 NULL，实体也是 `Integer`。列表展示时需要前端处理 null。如果业务要求楼层必填，应在 DTO 加 `@NotNull`。

5. **无软删除**：`delete` 是物理删除。如果需要保留操作轨迹，可加 `deleted` 字段做逻辑删除，配合 MyBatis-Plus 的 `@TableLogic`。

6. **房号全局唯一 vs 房型内唯一**：当前是全局唯一（`uk_room_no`）。如果不同楼层可以有相同房号（如 1 栋 201 和 2 栋 201），需要改成 `(building, room_no)` 联合唯一，但目前没有楼栋字段，所以全局唯一是合理的简化。
