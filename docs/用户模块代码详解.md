## 1. 模块概览

用户与认证模块是系统的“身份入口”，负责三件事：

1. **房客注册**：创建账号，密码加密入库；
2. **登录鉴权**：校验用户名密码，签发 JWT；
3. **当前用户查询**：用已登录态取用户信息。

核心设计是**房客和房东共用一张 `users` 表**，靠 `role` 字段区分（`CUSTOMER` 房客 / `HOST` 房东），而不是建两套表和两套登录体系。这样：

- 登录入口统一，前端不需要判断身份；
- 权限由后端在 `SecurityConfig` 里按 `role` 控制（`/api/admin/**` 仅 `HOST`）；
- 房东账号不是注册出来的，而是由系统初始化（演示数据 seeder）或手动插入，注册接口固定创建 `CUSTOMER`，避免房客自封房东。

模块本身不实现 JWT 的生成和解析，而是委托给 `security` 模块的 `JwtTokenProvider`；也不实现异常和统一响应，而是用 `common` 模块的 `BizException` / `ApiResponse`。user 模块只关注“用户数据 + 认证逻辑”。

## 3. 数据表设计

`users` 表在 `src/main/resources/db/schema.sql` 中定义：

```sql
CREATE TABLE IF NOT EXISTS users (
    id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    username    VARCHAR(50)  NOT NULL COMMENT '登录名',
    password    VARCHAR(100) NOT NULL COMMENT 'BCrypt 密文',
    nickname    VARCHAR(50)  NOT NULL COMMENT '昵称',
    phone       VARCHAR(20)  DEFAULT NULL COMMENT '手机号',
    role        VARCHAR(20)  NOT NULL DEFAULT 'CUSTOMER' COMMENT 'CUSTOMER 房客 / HOST 房东',
    status      TINYINT      NOT NULL DEFAULT 1 COMMENT '1 正常 0 禁用',
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_username (username)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户';
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增主键 |
| `username` | VARCHAR(50) | 登录名，**全局唯一** |
| `password` | VARCHAR(100) | BCrypt 哈希，**不存明文**。100 位足够容纳 BCrypt 的 60 位哈希 |
| `nickname` | VARCHAR(50) | 昵称，展示用 |
| `phone` | VARCHAR(20) | 手机号，可空 |
| `role` | VARCHAR(20) | 角色，默认 `CUSTOMER`；`HOST` 房东由 seeder 或手动创建 |
| `status` | TINYINT | `1` 正常 / `0` 禁用，默认 `1`；禁用后无法登录 |
| `created_at` / `updated_at` | DATETIME | 由 DB 默认值自动维护 |

唯一键 `uk_users_username (username)` 在数据库层面兜底用户名唯一性，即使应用层查重有并发漏洞，重复插入也会被唯一键拦截。

## 4. 实体层 entity：User

文件：`user/entity/User.java`

纯 POJO，用 MyBatis-Plus 注解映射 `users` 表。类注释点明两个关键约定：

1. 房客与房东共用一张表，靠 `role` 区分；
2. `status` 为 `0` 的账号禁用后无法登录。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `Long` | `@TableId(type = IdType.AUTO)` 自增主键 |
| `username` | `String` | 登录用户名 |
| `password` | `String` | BCrypt 密文，**对外永不返回** |
| `nickname` | `String` | 昵称 |
| `phone` | `String` | 手机号，可空 |
| `role` | `String` | `CUSTOMER` / `HOST` |
| `status` | `Integer` | `1` 正常 / `0` 禁用 |
| `createdAt` / `updatedAt` | `LocalDateTime` | 时间戳 |

所有方法都是标准 getter/setter。`password` 字段虽然在实体里存在，但转换为 `UserVO` 时会被丢弃，不会泄漏到接口响应。

## 5. 数据传输层 dto

### 5.1 `RegisterRequest`（注册请求）

Java 17 `record`，带 Jakarta Validation 注解，Controller 入参处用 `@Valid` 触发校验：

| 字段 | 校验 | 说明 |
| --- | --- | --- |
| `username` | `@NotBlank` `@Size(4-20)` `@Pattern("^[a-zA-Z0-9_]+$")` | 4–20 位，仅字母数字下划线 |
| `password` | `@NotBlank` `@Size(6-32)` | 6–32 位明文，入库前服务端加密 |
| `nickname` | `@NotBlank` `@Size(max=20)` | 昵称必填，最长 20 字符 |
| `phone` | `@Pattern("^$\|^1[3-9]\\d{9}$")` | 可空；填写时必须是 11 位大陆手机号 |

注意手机号的正则 `^$|^1[3-9]\d{9}$`：`^$` 分支允许空字符串通过，这样“不填手机号”不会被正则拦截，实现“可选但填了就必须合规”。

### 5.2 `LoginRequest`（登录请求）

只有两个必填字段：

```java
public record LoginRequest(
        @NotBlank String username,
        @NotBlank String password
) {}
```

房客和房东用同一登录入口，角色由账号本身的 `role` 决定，登录请求不区分身份。

### 5.3 `AuthResponse`（登录响应）

```java
public record AuthResponse(
        String token,           // JWT 访问令牌
        long expiresInMinutes,  // 有效期（分钟）
        UserVO user             // 当前用户信息（不含密码）
) {}
```

登录成功后一次性返回 token、有效期和用户信息。前端把 token 存到 `localStorage`，后续请求加在 `Authorization: Bearer {token}` 头里；`user` 用于前端判断角色和展示昵称。

### 5.4 `UserVO`（用户对外视图）

```java
public record UserVO(Long id, String username, String nickname, String phone, String role) {
    public static UserVO from(User user) {
        return new UserVO(user.getId(), user.getUsername(), user.getNickname(), user.getPhone(), user.getRole());
    }
}
```

关键设计：**故意没有 `password` 和 `status` 字段**。`password` 不返回是安全常识；`status` 不返回是因为前端不需要知道账号是否被禁用（禁用账号根本登录不了，拿不到 token）。静态工厂 `from` 集中做实体→视图的映射，确保敏感字段不会被遗漏地暴露。

## 7. 业务层 service：AuthService

文件：`user/service/AuthService.java`，约 87 行。用户模块全部业务逻辑都在这里。

### 7.1 依赖注入

```java
private final UserMapper userMapper;
private final PasswordEncoder passwordEncoder;   // Spring Security 提供的 BCrypt 编码器
private final JwtTokenProvider jwtTokenProvider; // security 模块的 JWT 工具
```

构造器注入三个依赖。`PasswordEncoder` 是 `SecurityConfig` 里声明的 `@Bean`（返回 `BCryptPasswordEncoder`），`JwtTokenProvider` 是 `security` 模块的组件。

### 7.2 `register` —— 房客注册

```java
@Transactional
public UserVO register(RegisterRequest request) {
    Long exists = userMapper.selectCount(new LambdaQueryWrapper<User>()
            .eq(User::getUsername, request.username()));
    if (exists > 0) {
        throw new BizException(ErrorCode.CONFLICT, "用户名已存在");
    }

    User user = new User();
    user.setUsername(request.username());
    user.setPassword(passwordEncoder.encode(request.password()));  // 明文 → BCrypt 哈希
    user.setNickname(request.nickname());
    user.setPhone(request.phone());
    user.setRole("CUSTOMER");   // 注册固定为房客，不允许自封房东
    user.setStatus(1);          // 默认正常
    userMapper.insert(user);
    return UserVO.from(user);
}
```

关键逻辑：

1. **先查重**：按用户名查计数，已存在抛 `CONFLICT`。这是应用层查重，数据库唯一键是兜底；
2. **密码加密**：`passwordEncoder.encode` 把明文转成 BCrypt 哈希后再入库，**绝不存明文**；
3. **角色固定 `CUSTOMER`**：注册接口写死角色，不接受前端传 `role`，从源头杜绝房客注册成房东；
4. **状态固定 `1`**：新账号默认正常，禁用是后台操作，注册时不允许选；
5. 返回 `UserVO.from(user)`，自动剥离密码。

### 7.3 `login` —— 登录

```java
public AuthResponse login(LoginRequest request) {
    User user = userMapper.selectOne(new LambdaQueryWrapper<User>()
            .eq(User::getUsername, request.username()));
    if (user == null || !passwordEncoder.matches(request.password(), user.getPassword())) {
        throw new BizException(ErrorCode.UNAUTHORIZED, "用户名或密码错误");
    }
    if (!Objects.equals(user.getStatus(), 1)) {
        throw new BizException(ErrorCode.FORBIDDEN, "账号已被禁用");
    }

    String token = jwtTokenProvider.createToken(new LoginUser(user.getId(), user.getUsername(), user.getRole()));
    return new AuthResponse(token, jwtTokenProvider.getExpireMinutes(), UserVO.from(user));
}
```

关键逻辑：

1. **按用户名查用户**：查不到直接进入密码比对的 `||` 短路，统一抛“用户名或密码错误”；
2. **密码比对用 `matches` 而非 `equals`**：BCrypt 哈希每次加盐不同，不能直接字符串比较，必须用 `passwordEncoder.matches(明文, 哈希)`；
3. **不区分“用户不存在”和“密码错误”**：两种情况返回相同的错误信息，避免攻击者通过报错差异枚举用户名；
4. **禁用账号单独拦截**：密码正确但 `status != 1` 时抛 `FORBIDDEN`（403），和 401 区分开——401 是凭证不对，403 是凭证对但没权限（账号被封）；
5. **签发 JWT**：把 `id / username / role` 封装成 `LoginUser` 传给 `JwtTokenProvider.createToken`，token 里只存这三个字段（见 9.2）。

### 7.4 `currentUser` —— 当前用户

```java
public UserVO currentUser(Long userId) {
    User user = userMapper.selectById(userId);
    if (user == null) {
        throw new BizException(ErrorCode.UNAUTHORIZED, "用户不存在");
    }
    return UserVO.from(user);
}
```

前端拿着 token 调用 `/api/auth/me` 时，`JwtAuthenticationFilter` 先解析出 `userId` 放进 `SecurityContext`，Controller 取出来传给这个方法查最新用户信息。用户不存在（比如被删了但 token 还没过期）时抛 `UNAUTHORIZED`，前端会跳登录页。

## 8. 控制层 controller：AuthController

文件：`user/controller/AuthController.java`

路径前缀 `/api/auth`，3 个端点：

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/api/auth/register` | 无需 | 房客注册 |
| `POST` | `/api/auth/login` | 无需 | 登录，返回 JWT |
| `GET` | `/api/auth/me` | 需登录 | 当前登录用户信息 |

`register` 和 `login` 由 `SecurityConfig` 加入白名单（`permitAll`），`/me` 需要携带有效 JWT。

`me` 方法取当前用户的方式：

```java
@GetMapping("/me")
public ApiResponse<UserVO> me(Authentication authentication) {
    LoginUser loginUser = (LoginUser) authentication.getPrincipal();
    return ApiResponse.ok(authService.currentUser(loginUser.id()));
}
```

Spring Security 在请求到达 Controller 前，由 `JwtAuthenticationFilter` 把解析出的 `LoginUser` 放进 `Authentication.getPrincipal()`。这里做了一次强转 `(LoginUser)`——因为系统自定义了 principal 类型，不是默认的 `UserDetails`。强转是安全的，因为过滤器只放能解析出有效 `LoginUser` 的请求进来。

## 9. 跨模块协作：依赖的 security 与 common

user 模块本身不实现安全细节，但强依赖另外两个公共模块：

### 9.1 common 模块

- `ApiResponse`：统一响应包装 `{ code, message, data }`，Controller 的返回值都用它；
- `BizException` + `ErrorCode`：业务异常。`CONFLICT`（409 用户名重复）、`UNAUTHORIZED`（401）、`FORBIDDEN`（403）都在 `ErrorCode` 里定义，由全局异常处理器转成 HTTP 状态码。

### 9.2 security 模块

- **`PasswordEncoder`**：`SecurityConfig` 声明的 `BCryptPasswordEncoder` Bean，负责 `encode`（注册）和 `matches`（登录）；
- **`JwtTokenProvider`**：JWT 生成与解析工具：
  - `createToken(LoginUser)`：把用户信息写进 JWT 的 claims；
  - `getExpireMinutes()`：返回配置里的 token 有效期（默认 1440 分钟 = 24 小时）；
  - 解析逻辑在 `JwtAuthenticationFilter` 里，请求到达时验证 token 有效性并构建 `SecurityContext`；
- **`LoginUser`**：自定义的 principal record，包含 `id`、`username`、`role` 三个字段。JWT 里只存这三个，不存密码等敏感信息；
- **`SecurityConfig`**：定义 URL 权限规则——`/api/auth/register`、`/api/auth/login`、`/api/public/**` 放行，`/api/admin/**` 需 `HOST` 角色，其余需登录。

依赖方向：**user 依赖 security 和 common，security/common 不依赖 user**。这样安全框架可以独立测试，用户模块只负责业务数据。

## 10. 认证全流程时序图

### 10.1 注册

```
前端              AuthController        AuthService          DB(users)
 │  POST /api/auth/register
 │ ──────────────►  register()
 │                                      │  selectCount 查重 ──► SELECT
 │                                      │  (冲突则抛 CONFLICT)
 │                                      │  passwordEncoder.encode
 │                                      │  insert (role=CUSTOMER) ──► INSERT
 │                                      │  return UserVO (无密码)
 │ ◄──────────────  { code:0, data:{id,username,...} }
```

### 10.2 登录

```
前端              AuthController        AuthService          JwtTokenProvider     DB
 │  POST /api/auth/login
 │ ──────────────►  login()
 │                                      │  selectOne by username ──► SELECT
 │                                      │  passwordEncoder.matches
 │                                      │  (失败抛 UNAUTHORIZED，不区分原因)
 │                                      │  校验 status==1 (禁用抛 FORBIDDEN)
 │                                      │  createToken(LoginUser) ──► 生成 JWT
 │                                      │  return AuthResponse
 │ ◄──────────────  { code:0, data:{token, expiresIn, user} }
```

### 10.3 鉴权访问（以 /me 为例）

```
前端（带 Authorization: Bearer xxx）        JwtAuthenticationFilter       AuthController
 │ ───────────────────────────────────────►  解析 token
 │                                              验证签名/过期
 │                                              构建 LoginUser → SecurityContext
 │                                            me(Authentication)
 │                                              取 principal.id → currentUser(id)
 │ ◄──────────────────────────────────────────  { code:0, data: UserVO }
```

token 无效或过期时，过滤器直接返回 401，请求不会到达 Controller。

## 11. 关键设计点

### 11.1 房客房东共用一表，角色固定

注册接口写死 `role = "CUSTOMER"`，房东账号只能通过 seeder 或数据库手动创建。这是一个刻意的安全设计：**注册路径永远不能产生房东**，避免越权。如果未来需要“申请成为房东”，应单独建审核流程，而不是放开注册时的 `role` 参数。

### 11.2 密码全程 BCrypt，从不明文

- 注册时 `encode` 入库；
- 登录时 `matches` 比对，不做字符串相等；
- 实体→视图转换时丢弃 `password`，接口响应永不返回密码；
- 数据库字段 `VARCHAR(100)` 容纳 60 位 BCrypt 哈希，留有余量。

### 11.3 登录错误不区分原因

“用户不存在”和“密码错误”返回同一句“用户名或密码错误”。这是防枚举的标准做法——攻击者无法通过响应差异判断某个用户名是否已注册。

### 11.4 禁用账号用 403 区分

密码正确但账号被禁用，返回 `FORBIDDEN`（403）而非 `UNAUTHORIZED`（401）。语义上：401 = 你是谁我不认；403 = 我知道你是谁，但你现在不能进。前端可以据此给用户更准确的提示（“您的账号已被禁用，请联系管理员”）。

### 11.5 JWT 只存最小必要信息

token 里只存 `id`、`username`、`role`，不存密码、手机号等敏感信息，也不存权限列表（权限由后端每次按角色实时判断，避免 token 权限过期问题）。`role` 存在 token 里是为了过滤器能快速做 URL 级角色拦截，不用每次查库。

### 11.6 应用层查重 + 数据库唯一键双层保护

用户名唯一性既在 `register` 里用 `selectCount` 查重（给友好提示），又在数据库建 `uk_users_username`（兜底防并发）。和 room 模块的房间号查重是同一套模式。

## 12. 边界与可改进点

1. **无登录失败次数限制**：当前 `login` 没有失败计数和锁定机制，理论上可被暴力破解。生产环境应加失败次数限制（如 5 次失败锁定 15 分钟）或接验证码。

2. **无 token 刷新机制**：token 有效期固定 24 小时，过期后必须重新登录。如果要提升体验，可加 refresh token 机制，或缩短 access token 有效期配合无感刷新。

3. **手机号未做唯一约束**：`phone` 字段没有唯一索引，注册时也不查重。如果业务要求手机号唯一（用于短信登录等），需要加唯一键并在注册时查重。

4. **房东账号无管理接口**：`HOST` 账号只能通过 seeder 或手动 SQL 创建，没有后台“用户管理”接口来创建/禁用房东。课程演示够用，生产需要补用户管理模块。

5. **`register` 返回的 `id` 等信息暴露**：注册成功返回了 `UserVO`（含 id），一般注册只需返回成功状态。不过 `UserVO` 不含敏感字段，风险较低，可接受。

6. **密码强度策略简单**：只校验了长度 6–32，没有要求大小写/数字/符号混合。演示够用，生产可加复杂度校验。

7. **无登出接口**：JWT 是无状态的，服务端没有 token 黑名单。“登出”目前只能靠前端删除本地 token。如果需要服务端强制下线，可加 Redis 黑名单。
